# feat(auth): [1.2] вход по JWT и роли клиента, механика, менеджера

## Задача и функционал

**ID:** 1.2 · **Эпик:** Пользователи и доступ · **Сервис:** auth-service · **Оценка:** 3 SP.

Пользователи всех трёх ролей входят по email и паролю, получают JWT access token
и обращаются к защищённым ручкам с `Authorization: Bearer <access_token>`.

- `POST /auth/login`: проверка Argon2-пароля, JSON с JWT, сроком в секундах и типом `bearer`.
  Email нормализуется как при регистрации. Неизвестный email и неверный пароль дают
  одинаковый `401`; для неизвестного email тоже выполняется проверка Argon2 с dummy-хешем.
- `GET /auth/me`: текущие ID, email, роль и дата создания. Доступно всем трём ролям.
  Пароля и его хеша в ответе нет.
- JWT: только HS256; проверяются подпись, expiry, issuer, audience, обязательные
  `sub`, `role`, `iat`, `exp`, `iss`, `aud`, допустимая роль и UUID пользователя.
  В токен не включаются пароль, хеш и email. Срок по умолчанию — 30 минут.
- Пользователь и актуальная роль читаются из БД. Удалённый аккаунт теряет доступ;
  понижение роли работает для старых токенов. Claim `role` — только снимок роли при входе.
- `require_roles(...)`: переиспользуемая зависимость для ограничения будущих бизнес-ручек.
  Недостаточная роль → `403`. Матрица трёх ролей и понижение роли проверены на тестовых маршрутах,
  которые **не подключены к рабочему API**. `/auth/me` доступен всем трём ролям.
- CLI `uv run python -m app.cli create-staff`: создание механика/менеджера со скрытым вводом пароля.
  Не меняет роль существующего аккаунта, не допускает публичного повышения привилегий.
- `JWT_SECRET` обязателен, не короче 32 символов; секрет по умолчанию не задан.
  Успешный ответ входа содержит `Cache-Control: no-store` и `Pragma: no-cache`.

Новых миграций нет: роли уже предусмотрены миграцией `0001`. Применить её всё равно нужно.
Не входят в PR: профиль с именем/телефоном (1.3), refresh-токены, logout, индивидуальный
отзыв токенов, подтверждение email и восстановление пароля.
Файлы GitHub Actions не добавлялись и не изменялись.

## Подготовка проверки

Python 3.12–3.14, PostgreSQL 17 либо Docker Desktop; uv подберёт Python сам.
Команды из папки `backend`:

```powershell
uv sync
# Только если .env ещё нет:
Copy-Item .env.example .env
uv run python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Вставьте сгенерированное значение в `JWT_SECRET` файла `.env`. Существующий `.env`
не перезаписывайте: добавьте JWT-настройки вручную. Тестовые пароли и токены не публикуйте.

| Переменная | Настройка |
| --- | --- |
| `DATABASE_URL` | Подключение к PostgreSQL, как в задаче 1.1 |
| `JWT_SECRET` | Обязательный случайный секрет от 32 символов |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | 30 по умолчанию; для проверки expiry можно задать 1 |
| `JWT_ISSUER` | `rps-auth-service` по умолчанию |
| `JWT_AUDIENCE` | `rps-api` по умолчанию |

```powershell
docker compose up -d db
uv run scripts/manage.py migrate
uv run scripts/manage.py run
```

При существующем PostgreSQL Compose не нужен; задайте его URL.
Для JWT-настроек требуется перезапуск API. Пустой/короткий секрет — ошибка конфигурации,
а не `401`: JWT-настройки проверяются при первом обращении к login/защищённым ручкам.
Публичные health и регистрация не требуют JWT-настроек.

Base URL: `http://127.0.0.1:8000`. Swagger: `http://127.0.0.1:8000/docs`.

Создайте клиента через `POST /auth/register`, например `qa.client@example.com`
с тестовым паролем `ExamplePass123!`. Для сотрудников:

```powershell
uv run python -m app.cli create-staff --email qa.mechanic@example.com --role mechanic
uv run python -m app.cli create-staff --email qa.manager@example.com --role manager
```

Введите пароль дважды в интерактивном терминале; он не отображается и не передаётся
в аргументах команды. Используйте новый email для каждого нового аккаунта.
CLI: код `0` — создан; `1` — email занят/ошибка БД; `2` — неверные параметры/пароль.
Пароль — 8–128 символов, внешние пробелы сохраняются.

## Ручки для тестировщика

| Метод | Путь | Функционал | Авторизация / роль | Успех | Ошибки |
| --- | --- | --- | --- | --- | --- |
| POST | `/auth/login` | Получение JWT по email и паролю | Не нужна; аккаунт любой из трёх ролей | `200` | `401`, `422` |
| GET | `/auth/me` | Текущая учётная запись и роль | Bearer JWT; `client`, `mechanic`, `manager` | `200` | `401` |

`POST /auth/register` из задачи 1.1 используется для подготовки клиента, его контракт сохранён.
Ролевых бизнес-ручек пока нет; `403` проверяется автоматическими тестами зависимости
`require_roles`, а не запросом к `/auth/me`.

### Вход

```http
POST /auth/login HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json

{"email":"qa.client@example.com","password":"ExamplePass123!"}
```

Ответ `200 OK`, `Content-Type: application/json`, `Cache-Control: no-store`, `Pragma: no-cache`:

```json
{"access_token":"<JWT access token>","token_type":"bearer","expires_in":1800}
```

`expires_in` зависит от настройки TTL. Вход принимает JSON, а не form-data.
Неверный пароль либо неизвестный валидный email: `401`, `WWW-Authenticate: Bearer`:

```json
{"detail":"Invalid email or password"}
```

Неверный формат email, пустой/отсутствующий пароль, пароль длиннее 128 символов,
пароль-число или дополнительные поля (включая `role`) дают `422`.
Непустой неверный пароль длиной до 128 символов даёт `401`, даже если он короче 8 символов.
В ошибках валидации есть только `type`, `loc`, `msg`, без входных значений.

### Текущая учётная запись

```http
GET /auth/me HTTP/1.1
Host: 127.0.0.1:8000
Authorization: Bearer <access_token из login>
```

Ответ `200 OK` (ID и время ниже — примеры):

```json
{
  "id":"c905f54c-dfc1-4e91-8d95-1386a340d8de",
  "email":"qa.client@example.com",
  "role":"client",
  "created_at":"2026-11-17T12:00:00Z"
}
```

Для сотрудника вернётся соответственно `mechanic` или `manager`.
Тело запроса не требуется. Пароль, хеш и дополнительные данные профиля отсутствуют.
Без токена или с неподдерживаемой схемой авторизации: `401 {"detail":"Not authenticated"}`.
Невалидный/просроченный токен, неизвестный UUID или удалённый аккаунт:
`401 {"detail":"Invalid or expired token"}`. В обоих случаях `WWW-Authenticate: Bearer`.

PowerShell:

```powershell
$loginBody = @{ email = "qa.client@example.com"; password = "ExamplePass123!" } | ConvertTo-Json
$loginResult = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/auth/login `
  -ContentType "application/json" -Body $loginBody
Invoke-RestMethod -Uri http://127.0.0.1:8000/auth/me `
  -Headers @{ Authorization = "Bearer $($loginResult.access_token)" }
```

Swagger: выполнить login, скопировать `access_token`, нажать **Authorize**, вставить
только токен без префикса `Bearer`, затем выполнить `/auth/me`.

## Сценарии проверки

| № | Предусловия | Действие | Ожидаемый результат |
| --- | --- | --- | --- |
| 1 | Клиент создан | Войти с корректными данными | `200`, JWT, `bearer`, TTL в секундах |
| 2 | Получен токен клиента | GET `/auth/me` с Bearer | `200`, свой ID/email, роль `client` |
| 3 | Созданы механик и менеджер через CLI | Для каждого повторить login и me | `200`, роли `mechanic`/`manager` |
| 4 | Клиент существует | Вход с email в другом регистре и внешними пробелами | `200`, тот же аккаунт |
| 5 | Любое | Неверный пароль; затем неизвестный валидный email | Одинаковые `401` и JSON `Invalid email or password` |
| 6 | Любое | Невалидный email, пустой пароль, отсутствующее поле или лишняя роль | `422`, без входных значений и JWT |
| 7 | Любое | GET `/auth/me` без токена, с `Basic`, с пустым `Bearer` | `401`, заголовок `WWW-Authenticate: Bearer` |
| 8 | Есть JWT | Изменить символ в середине токена; запросить me | `401`, без данных пользователя |
| 9 | TTL=1 минута, API перезапущен | Получить новый токен, проверить me, подождать более 60 секунд и повторить | Сначала `200`, затем `401` |
| 10 | Тестовый аккаунт создан | Удалить только этот аккаунт в тестовой БД, запросить me со старым токеном | `401` |
| 11 | Получен JWT | Сменить `JWT_SECRET`, перезапустить API, запросить me | Старый токен → `401`; новый login → рабочий токен |
| 12 | Существующий клиент | Выполнить create-staff с его email и ролью manager | Код CLI `1`, роль клиента не меняется |
| 13 | Новый email сотрудника | Ввести несовпадающие или слишком короткие пароли | Код CLI `2`, аккаунт не создаётся |
| 14 | Swagger открыт | Авторизоваться и выполнить me | `200`, секретных полей в ответе нет |

Проверку удаления делайте только с созданным для этого тестовым аккаунтом.
Изменение TTL применяется к новым токенам; прежние не становятся короче автоматически.
После сценариев 9/11 верните локальные настройки и перезапустите API.

Автоматически проверяются все сочетания ролей (3×3), общие разрешённые роли,
`403 {"detail":"Insufficient permissions"}` при недостаточных правах и понижение роли
со старым токеном. Тестовые endpoint'ы `/test-*` в рабочем приложении отсутствуют.
