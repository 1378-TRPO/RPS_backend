# feat(auth): [1.1] регистрация клиента по email и паролю

## Задача и функционал

**ID:** 1.1 · **Эпик:** Пользователи и доступ · **Сервис:** auth-service · **Оценка:** 2 SP.

Добавлена публичная регистрация клиента. `POST /auth/register` принимает email и пароль,
создаёт пользователя с ролью `client` и возвращает `201` с ID, email, ролью и временем создания.
Пароль хранится как Argon2id-хеш с индивидуальной солью. Пароль и хеш в ответах отсутствуют.

Email валидируется, обрезаются внешние пробелы, весь адрес приводится к нижнему регистру.
Уникальность защищена БД; повторный адрес, включая другой регистр, возвращает `409`.
Обработан конфликт уникальности, если другая регистрация успевает занять адрес между
проверкой и вставкой. Другие ошибки БД не маскируются под конфликт email.

Принимаются только поля `email`, `password`; передача роли или других полей запрещена.
Пароль — 8–128 символов без обрезания пробелов; требований к набору символов пока нет.
Email — до 254 символов. Ошибочные запросы возвращают `422` без исходных входных значений.

Добавлены модель пользователя, миграция `0001`, документация API, тесты и зависимости
`pwdlib[argon2]`, `email-validator`. Сценарии строят тестовую схему через Alembic;
данные тестов изолированы транзакциями. Секретные значения удалены из **всех** ответов
`RequestValidationError`: ошибки содержат только `type`, `loc`, `msg`.

Не входит в PR: вход/JWT и управление ролями (1.2), профиль (1.3), подтверждение email,
восстановление пароля, refresh-токены. Роли mechanic/manager предусмотрены моделью,
но публичная регистрация их не создаёт.

## Подготовка проверки

Нужны Python 3.13 и PostgreSQL 17 (или Docker Desktop). Из папки репозитория, PowerShell:

```powershell
# Только если .venv ещё нет:
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
# Только если .env ещё нет:
Copy-Item .env.example .env
docker compose up -d db
.\.venv\Scripts\python.exe scripts/manage.py migrate
.\.venv\Scripts\python.exe scripts/manage.py run
```

При существующем PostgreSQL вместо Compose задайте `DATABASE_URL` в `.env`.
Миграция `0001` создаёт `users`: UUID, уникальный email, хеш пароля, роль и дату создания.
Для полного отката на тестовой БД: `python -m alembic downgrade base` — **удаляет `users`
вместе с данными**. Для обычной проверки откат не требуется.

Base URL: `http://127.0.0.1:8000`. Swagger: `http://127.0.0.1:8000/docs`.
OpenAPI: `http://127.0.0.1:8000/openapi.json`.
Предварительные аккаунты, роли и токены не нужны. Для каждого нового успешного сценария
используйте новый email. Ниже тестовые, а не реальные реквизиты.

## Ручки для тестировщика — обязательно

| Метод | Путь | Функционал | Токен / роль | Успех | Ошибки |
| --- | --- | --- | --- | --- | --- |
| POST | `/auth/register` | Регистрация клиента по email и паролю | Не нужны | `201 Created` | `409 Conflict`, `422 Unprocessable Content` |

Заголовок: `Content-Type: application/json`. `Authorization` не требуется.

### Успешная регистрация

```http
POST /auth/register HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json

{"email":"qa.client@example.com","password":"ExamplePass123!"}
```

Ответ `201 Created`, `Content-Type: application/json`:

```json
{
  "id": "c905f54c-dfc1-4e91-8d95-1386a340d8de",
  "email": "qa.client@example.com",
  "role": "client",
  "created_at": "2026-11-17T12:00:00Z"
}
```

ID и время — примеры, фактические значения формируются сервером.
Поля `password`, `password_hash`, `access_token` отсутствуют.

PowerShell:

```powershell
$registrationBody = @{ email = "qa.client@example.com"; password = "ExamplePass123!" } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/auth/register `
  -ContentType "application/json" -Body $registrationBody
```

### Повторный email

Повторить тот же запрос или заменить адрес на `QA.CLIENT@EXAMPLE.COM`.
Ответ `409 Conflict`:

```json
{"detail":"Email already registered"}
```

### Ошибка валидации

Запрос `{"email":"qa.client@example.com"}` (нет обязательного пароля).
Ответ `422`, без исходных входных значений:

```json
{
  "detail": [
    {"type":"missing","loc":["body","password"],"msg":"Field required"}
  ]
}
```

Для других ошибок `type`, `loc`, `msg` соответствуют нарушенному условию.
В ответе не должно быть `input`, `ctx`, пароля или тела запроса.

## Сценарии ручной проверки

| № | Предусловие | Действие / данные | Ожидаемый результат |
| --- | --- | --- | --- |
| 1 | Email ещё не занят | Корректный запрос из примера | `201`, корректный UUID, время, email, роль `client` |
| 2 | Создан пользователь из №1 | Повторить запрос | `409`, `Email already registered`, без второго пользователя |
| 3 | Создан пользователь из №1 | Email `QA.CLIENT@EXAMPLE.COM` | `409`, без второго пользователя |
| 4 | Новый email | Адрес ` Qa.New@Example.COM ` | `201`, email в ответе `qa.new@example.com` |
| 5 | Любое | Email `not-an-email` | `422`, пользователь не создаётся |
| 6 | Новый email | Пароль из 7 символов, затем из 129 | Оба запроса → `422`, пользователь не создаётся |
| 7 | Разные новые email | Пароли из ровно 8 и 128 символов | Оба запроса → `201` |
| 8 | Новый email | Нет email или пароля, либо значение `null` | `422`, пользователь не создаётся |
| 9 | Новый email | Добавить `role: manager`, затем `mechanic`, затем `client` | Каждый запрос → `422`, роль нельзя передать даже как `client` |
| 10 | Новый email | Добавить `id` или `password_hash` | `422`, пользователь не создаётся |
| 11 | Любое | Некорректный JSON или пароль-число | `422`, без эха пароля и тела запроса |
| 12 | Выполнены №1–11 | Проверить JSON всех ответов | Пароль, хеш и JWT отсутствуют; в ошибках нет входных значений |
| 13 | Приложение запущено | Открыть `/docs` | Ручка публичная, видны тело запроса и ответы `201`, `409`, `422` |

Для проверок ниже нужен доступ к **тестовой** БД:

```sql
SELECT id, email, role, created_at,
       password_hash LIKE '$argon2id$%' AS uses_argon2id
FROM users
WHERE email = 'qa.client@example.com';
```

Ожидание: одна запись, роль `client`, `uses_argon2id = true`. Проверка соответствия
хеша исходному паролю и индивидуальных солей выполняется автоматическими тестами.
Конфликт вставки после устаревшей проверки email также покрыт автоматическим тестом.
