# feat(users): [1.3] профиль клиента — имя, телефон и email

## Задача и функционал

**ID:** 1.3 · **Эпик:** Пользователи и доступ · **Сервис:** auth-service · **Оценка:** 1 SP.

Клиент может просмотреть и изменить свой профиль. Добавлены `GET /users/me`,
`PATCH /users/me` и миграция `0002` с nullable-полями `name`, `phone` таблицы `users`.
Существующие аккаунты, email, пароль и роль сохраняются; новые поля изначально `null`.
При регистрации по-прежнему принимаются только email и пароль.

Пользователь определяется по UUID в JWT, без параметра чужого ID. Доступ — только `client`.
Механик/менеджер получают `403`; их `/auth/me` остаётся доступен.
В профиле возвращаются только `id`, `name`, `phone`, `email`.

Частичный PATCH сохраняет неуказанные поля. `null` очищает имя/телефон, но не email.
Имя обрезается по краям, длина 1–100 символов. Телефон — `+` и 7–15 цифр ASCII,
первая цифра не `0`, внешние пробелы обрезаются. Скобки, дефисы и внутренние пробелы
не принимаются; реальность номера/владение не проверяются.

Email валидируется и нормализуется как при регистрации, уникален среди всех ролей.
Свой текущий email допустим. Конфликт → `409`, в том числе при конфликте вставки/обновления
после первоначальной проверки. Все изменения атомарны; при ошибке имя/телефон тоже не меняются.
Роль, пароль, ID и другие поля менять нельзя. Пустой `{}` и неверные значения → `422`
без эха исходных значений. OpenAPI показывает email необязательным, но не nullable.

После смены email вход работает по новому адресу с прежним паролем, по старому — `401`.
Ранее выданный JWT остаётся привязан к тому же ID, даже если старый email займёт другой клиент.
Подтверждение email/телефона и административное редактирование чужих профилей не входят в MVP.
Новых зависимостей нет. Файлы GitHub Actions не менялись.

## Подготовка проверки

Python 3.13, PostgreSQL 17 или Docker Desktop. Из папки репозитория:

```powershell
# Если окружение ещё не создано:
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
# Если .env ещё нет:
Copy-Item .env.example .env
```

Настройте `DATABASE_URL` и случайный `JWT_SECRET` не короче 32 символов.
Не перезаписывайте настроенный `.env`. Для генерации JWT-секрета:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))"
```

Вставьте результат в `.env`, затем:

```powershell
docker compose up -d db
.\.venv\Scripts\python.exe scripts/manage.py migrate
.\.venv\Scripts\python.exe scripts/manage.py run
```

Для существующего PostgreSQL Compose не нужен. Требуется миграция **0002**.
На БД версии `0001` миграция добавляет только имя/телефон и сохраняет аккаунты.
Откат `python -m alembic downgrade 0001` удаляет эти два поля и их значения,
но не аккаунты; для обычной проверки откат не нужен.

Base URL: `http://127.0.0.1:8000`. Swagger: `http://127.0.0.1:8000/docs`.

Создайте двух клиентов через `/auth/register` с разными email, например
`qa.profile@example.com` и `qa.other@example.com`, с тестовым паролем `ExamplePass123!`.
Войдите через `/auth/login`, получите отдельный JWT каждого клиента.
Для проверок роли создайте сотрудника служебной командой из задачи 1.2 и войдите под ним.
Примеры ниже используют только вымышленные тестовые данные.

## Ручки для тестировщика

| Метод | Путь | Функционал | Авторизация / роль | Успех | Ошибки |
| --- | --- | --- | --- | --- | --- |
| GET | `/users/me` | Свой профиль клиента | `Authorization: Bearer <access_token>`, `client` | `200` | `401`, `403` |
| PATCH | `/users/me` | Частичное изменение имени, телефона, email | Bearer JWT, `client` | `200` | `401`, `403`, `409`, `422` |

Связанные ручки для подготовки: `POST /auth/register`, `POST /auth/login`.
`GET /auth/me` возвращает учётную запись всех трёх ролей, его контракт сохранён.
В Swagger выполните login, скопируйте `access_token`, нажмите **Authorize** и вставьте
только токен без префикса `Bearer`.

### Просмотр

```http
GET /users/me HTTP/1.1
Host: 127.0.0.1:8000
Authorization: Bearer <токен клиента>
```

Тело запроса не требуется. Ответ нового клиента — `200 OK`, `Content-Type: application/json`:

```json
{
  "id":"c905f54c-dfc1-4e91-8d95-1386a340d8de",
  "name":null,
  "phone":null,
  "email":"qa.profile@example.com"
}
```

ID — пример, фактический UUID определяется сервером. Пароль, хеш и роль в ответе отсутствуют.

### Изменение

```http
PATCH /users/me HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json
Authorization: Bearer <токен клиента>

{"name":"  Иван Петров  ","phone":"+79991234567","email":" Qa.New@Example.COM "}
```

Ответ `200 OK`:

```json
{
  "id":"c905f54c-dfc1-4e91-8d95-1386a340d8de",
  "name":"Иван Петров",
  "phone":"+79991234567",
  "email":"qa.new@example.com"
}
```

Пример частичного изменения: `{"name":"Пётр"}` — телефон/email не меняются.
Пример очистки: `{"name":null,"phone":null}` — email не меняется.
Пустая строка не заменяет `null` и для имени/телефона даёт `422`.

PowerShell, после login из предыдущей задачи:

```powershell
$profileHeaders = @{ Authorization = "Bearer $($loginResult.access_token)" }
Invoke-RestMethod -Uri http://127.0.0.1:8000/users/me -Headers $profileHeaders
$profileBody = @{ name = "Иван Петров"; phone = "+79991234567" } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Uri http://127.0.0.1:8000/users/me `
  -Headers $profileHeaders -ContentType "application/json; charset=utf-8" `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($profileBody))
```

### Ошибки

- Без токена: `401 {"detail":"Not authenticated"}`.
- Поддельный/истёкший токен либо удалённый аккаунт:
  `401 {"detail":"Invalid or expired token"}`. У `401` есть `WWW-Authenticate: Bearer`.
- Токен механика/менеджера: `403 {"detail":"Insufficient permissions"}`.
- Email другого клиента, механика или менеджера:
  `409 {"detail":"Email already registered"}`, без частичного сохранения других полей.
- Невалидные данные, `email:null`, лишние поля или `{}`: `422`.
  В `detail` — список объектов `type`, `loc`, `msg`, без исходных значений.

## Сценарии проверки

| № | Предусловие | Действие / данные | Ожидаемый результат |
| --- | --- | --- | --- |
| 1 | Новый клиент с JWT | GET `/users/me` | `200`, свой ID/email, `name=null`, `phone=null` |
| 2 | JWT клиента | PATCH с корректными именем/телефоном/email, затем GET | Оба `200`, данные сохранены и нормализованы |
| 3 | Профиль заполнен | PATCH только `name` | `200`, телефон/email сохранены |
| 4 | Имя/телефон заполнены | PATCH `{"name":null,"phone":null}` | `200`, очищены только эти поля |
| 5 | JWT клиента | PATCH со своим email в другом регистре | `200`, не считается конфликтом |
| 6 | Есть другой аккаунт | PATCH с его email и новым именем | `409`, ни имя, ни email не изменены |
| 7 | JWT клиента | `{}`, `email:null`, пустой email, неверный формат email | `422`, профиль сохранён без изменений |
| 8 | JWT клиента | Пустое/пробельное имя или 101 символ | `422`; имя в 100 символов принимается |
| 9 | JWT клиента | Телефон без `+`, с пробелами внутри, скобками, дефисами, начальным 0, 6 или 16 цифрами | `422`, данные не меняются |
| 10 | JWT клиента | Телефон `+` с 7 и 15 цифрами, первая не 0 | `200`; проверяется формат, не реальность номера |
| 11 | JWT клиента | Добавить `role`, `password`, `password_hash`, `id` или другой атрибут | `422`, значения не отражаются в ошибке, роль/пароль не меняются |
| 12 | Нет JWT / токен испорчен | GET и PATCH профиля | `401`, без данных профиля |
| 13 | JWT механика или менеджера | GET и PATCH профиля | `403`; `/auth/me` по-прежнему `200` |
| 14 | JWT двух клиентов | GET каждого; попытка передать чужой ID в PATCH | Каждый видит себя; PATCH с ID → `422`, чужие данные не меняются |
| 15 | Email успешно изменён | Войти по новому и старому адресу | Новый → `200`; старый → `401`, пароль прежний |
| 16 | Email изменён, старый JWT сохранён | GET с прежним JWT | `200`, тот же UUID и новый email |
| 17 | БД версии 0001 с аккаунтами | Применить миграцию 0002 | Аккаунты/пароли/роли сохранены, новые поля `null` |
| 18 | Swagger открыт | Проверить обе ручки и ответы | Требуется Bearer, описаны `200/401/403`, у PATCH также `409/422` |

JWT с `sub`, содержащим постоянный ID, не даёт доступ к новому аккаунту, занявшему старый email.
Этот сценарий и конфликт email после устаревшей предварительной проверки покрыты тестами.
